## Category B — EmerAllJett cover interlock (EXPECTED — no fix needed)

**Control:** `JETTISON_SYSTEM.EmerAllJett`

The emergency jettison button sits under a spring-loaded cover (`EmerAllJettCap`). The
validation script opens all covers/guards before testing, but the cover and button are
separate controls — opening the cover does not make the button reachable until the cover
animation completes. The button itself is a momentary `default_button` with a stop_action;
arg 246 springs back to 0.0 on release, so pos 1 (1.0) is never the settled state.
`EmerAllJettCap` passes fine. **Acknowledged as expected.**

## Category C — DragChuteHandle is a forward-only state-machine cycle (EXPECTED — no fix needed)

**Control:** `CPT_MECH.DragChuteHandle`

The drag chute T-handle cycles through 4 states via left-click only:

| State | Arg | Description |
|-------|-----|-------------|
| 0 | 0.0 | Stowed, original orientation |
| 1 | 0.3 | Partly pulled out, same orientation |
| 2 | 0.7 | Partly pulled out, rotated |
| 3 | 1.0 | Fully pulled out, rotated (transient — returns to 0.7 on release) |

Right-click does nothing. Each simulated `performClickableAction` call (which DCS treats
as press + update tick + release) advances the arg by 0.3, not 0.1.

The mapping (`type: relative, wheel: true, incrementValue: 0.1, decrementValue: -0.1`) is
structurally correct — `incrementValue: 0.1` is the literal argValue in the Lua element.
However, the validation wheel test expects `arg + 0.1` after one increment send and
`arg - 0.1` after one decrement send; neither assertion holds for this control. The state
machine positions (0.3, 0.7, 1.0) are encoded in DCS C++ logic, not in `clickabledata.lua`.
**Acknowledged as expected — no accurate unit test possible for this control.**

## Category D — IFF CODE selector arg199: FIXED + gated position limitation (EXPECTED)

**Control:** `IFF.PTR-IFFCP-CODE-199_arg199`

Original failure: `pos 0: expected -1.0000, got 0.2000; pos 1: expected 0.0000, got 0.2000`

**Mapping fix applied.** Live-probed in DCS (2026-05-16). Sending command -1 from position
B (0.1) advances to A (0.2) then HOLD (0.3); sending +1 retreats. The BTN sub-control
argLims `[-1,0]`/`[0,1]` in the Lua are mouse-drag regions, not arg ranges. The custom
`_iffCode4` handler in `map_F5E.py` overrides argLim to the live-probed actual range.

Live-probed positions:

| Position | Arg | Notes |
|----------|-----|-------|
| ZERO | 0.0 | Gated — requires arg197=1.0 (knob pulled) before send -1 from B |
| B | 0.1 | Default resting position |
| A | 0.2 | Normal armed position |
| HOLD | 0.3 | Springloaded — returns to A on button release |

Corrected mapping: `type=relative, wheel=true, argLim=[0.0, 0.3], incrementValue=-1.0, decrementValue=1.0`

**Remaining validation limitation — gated ZERO position.**
Reaching ZERO (0.0) requires setting `arg197=1.0` via the companion lever first. The
standard wheel test does not perform prerequisite setup, so the decrement-past-B step will
fail validation. **Acknowledged as expected — mapping is correct, validation limitation only.**

## Category E — IFF MASTER selector pos 4 gated by knob-pull (EXPECTED — no fix needed)

**Control:** `IFF.PTR-IFFCP-MASTER-200_arg200`

Validation failure: `pos 4: expected 0.4000, got 0.3000`

The EMER position (pos 4, arg=0.4) requires the companion `arg198` mouse-wheel lever to be
set to 1.0 (knob pulled) before the TUMB command can reach it. Positions 0–3 (OFF/STBY/LOW/NORM,
args 0.0–0.3) work correctly in DCSControlPanel without any prerequisite.

The 5-position mapping (`argLim=[0.0, 0.4]`, `step=0.1`) is correct. The standard discrete
position test does not perform prerequisite setup, so pos 4 will always fail validation.
**Acknowledged as expected — mapping is correct, validation limitation only.**

## Category F — GunsMslCamrCover forced open by GunsMslCamr switch (EXPECTED — no fix needed)
