## Category A — Backup ADI argLim (EXPECTED — no fix needed)

**Controls:** `FLINST.art_hor_adj`, `FLINST.rc_art_hor_adj`

Actual free-movement range is ±0.95, not ±1.0. The full ±1.0 range is only reachable
transiently while the knob is pulled out (uncaged state). The knob snaps to 0.0 (uncaged)
when released at the bottom and to 0.7 (caged) when released at the top. This is correct
mechanical simulation behavior — the extraction reports argLim [-1.0, 1.0] which matches the
Lua definition, but the stable interactive range is [-0.95, 0.95]. **Acknowledged as expected.**

## Category C — CAS switch springloaded RESET position (EXPECTED — no fix needed)

**Controls:** `FLCTRL.cmd_3452` (Yaw CAS), `FLCTRL.cmd_3453` (Roll CAS), `FLCTRL.pitch_sw` (Pitch CAS)

These are 3-position switches (OFF=0.0, RESET=0.25, ON=0.5) where RESET is springloaded — it
momentarily moves to 0.25 then immediately returns to ON (0.5). The validator sends 0.25 expecting
the arg to settle there, but it springs back to 0.5 before the read. The control mapping
(3 positions, step=0.25, argLim=[0.0, 0.5]) is correct. **Acknowledged as expected.**

## Category D — WSO nuclear consent switch blocked by cover (EXPECTED — no fix needed)

**Controls:** `FLINST.cmd_3453` (WSO nuclear consent switch), `FLINST.cmd_3452` (WSO nuclear consent cover)

The WSO switch cover (`FLINST.cmd_3452`) does not have 'cover' in its name, so the validator
did not open it before testing the switch — the switch couldn't move. Both controls work
correctly in DCSControlPanel. DCS does not model nuclear weapons; the switch is cosmetic only.
The pilot-seat equivalents (`FLINST.nuc_sw`, `FLINST.nuc_cover`) are correctly named.
**Acknowledged as expected.**

## Category G — Show/Hide Controls device-internal cycling (EXPECTED — no fix needed)

**Control:** `CNPYSYST.cmd_3001`

The native Lua defines this as a plain `default_2_position_tumb` (`arg_value={1,-1}`,
`arg_lim={{0,1},{0,1}}`), so the generator correctly maps it as discrete with 2 positions and
argLim=[0,1]. However, the device internally cycles through three states (0.0 = stick+throttle
visible, 0.3 = stick hidden, 0.8 = both hidden) each time +1 is sent; -1 does nothing. The
cycling logic is compiled into the device binary — it is invisible to Lua extraction and cannot
be derived from native data. The control cannot be set to a specific position directly; it can
only be incremented one step at a time. The validator's sweep test cannot test this correctly.
**Acknowledged as expected.**
