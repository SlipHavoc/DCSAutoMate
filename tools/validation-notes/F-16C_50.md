### Validator guard-detection fix

An initial run scored 515/535 with 6 switch failures. Investigation showed 4 of those were guard-cover controls the validator's auto-open pass was missing:

- `ENGINE_INTERFACE.EngContSw` (guarded by `EngContSwCvr`)
- `ENGINE_INTERFACE.EpuSw` (guarded by `EpuSwCvr`)
- `FUEL_INTERFACE.FuelMasterSw` (guarded by `FuelMasterSwCvr`)
- `INTERCOM.ZeroizeSw` (guarded by `ZeroizeSwCvr`)

The F-16C uses the abbreviation `Cvr` in control names; the validator's `GUARD_KEYWORDS` only matched `'cover'` and `'guard'`. Added `'cvr'` to the keyword list in [`tools/validateControlMapping.py`](../validateControlMapping.py). Cross-module verification: adds 5 new guards for F-16C and 7 for Mi-24P (operator-side `Cvr` variants); zero false positives on other modules. After the fix, all 4 guarded-switch failures pass automatically.

Description-based matching was tried and rejected: FA-18C fire handles and `SpinRec` have descriptions that mention "cover" without being guards themselves, causing false positives. Name-only matching is the robust rule.

### FuelQtySelSw — 6-position rotary with absolute-set

Live probing (`C:4:3005:<v>` + arg 158 polling, F-16C air-start active-pause) confirmed that command 3005 accepts absolute values 0.0–0.5 for direct-to-position jumps (verified 0.1, 0.2, 0.3, 0.5). This matches the DCS source: `Input/F-16C/keyboard/default.lua` binds each of the six positions with `value_down = 0.0..0.5`, and `Macro_sequencies.lua` uses the same absolute values in cockpit-check macros. Earlier probe misreads (out-of-range 1.0 clamp, no-op 0.1 from current 0.1) were dispelled by the Lua audit.

| Position (CW order) | arg 158 |
|---|---|
| TEST | 0.0 (momentary, springs back to NORM) |
| NORM | 0.1 |
| RSVR | 0.2 |
| INT WING | 0.3 |
| EXT WING | 0.4 |
| EXT CTR | 0.5 |

Canonical entry `FUEL_INTERFACE.FuelQtySelSw` is now a 6-position `positionMap` with all six entries on `{deviceId: 4, commandId: 3005}` at `value: 0.0..0.5`. The validator's two failure modes (momentary-TEST springback, idempotent current-position) are inherent to DCS sim behavior, not mapping limitations.

The F-16C.py script has been updated to use the four native DCS ICP dobber canonicals (`UFC.DCS_UP/DOWN/RTN/SEQ`) and the two ICP DED increment/decrement canonicals (`UFC.DED_INC/DED_DEC`), accessed via the aliases `ICP_DCS_UP/DOWN/RTN/SEQ` and `ICP_DED_INC/DEC`.

## Known gaps

### 1. ICP data-switch rewrites — **completed**

The script previously used two synthetic 3-position momentary switches (`ICP_DATA_UP_DN_SW` and `ICP_DATA_RTN_SEQ_SW`) modeled after the old DCS-BIOS convention with values `{0: left/down, 1: center, 2: right/up}`. In the F-16C DCS module the ICP dobber is physically **four independent 2-position momentary buttons** sharing two args (184 for RTN/SEQ, 185 for UP/DN): `UFC.DCS_UP`, `UFC.DCS_DOWN`, `UFC.DCS_RTN`, `UFC.DCS_SEQ`. Each takes `1` to press and `0` to release, same pattern as the other ICP buttons.

The script has been rewritten to call the four native canonicals directly (via the aliases `ICP_DCS_UP/DOWN/RTN/SEQ`). The `ICP_DED_SW` alias — which had been incorrectly pointing to `MMC.DedData` (HUD DED/PFLD display switch on device 19, a different physical control) — was replaced with `ICP_DED_INC`/`ICP_DED_DEC` → `UFC.DED_INC`/`UFC.DED_DEC` (the correct increment/decrement paddle on UFC device 17, arg 183).

### 2. Indication field completeness — partial (inherent DCS limitation)

The JSON now has 1806 indication fields across 15 indications (HUD, DED, MFD-L, MFD-R, Fault, EHSI, CMDS, RWR, FCR/TGP, HMD, radio pages). Each indication only populates a subset of fields depending on the active page/mode at validation time. A full validation would require running separate passes with each relevant page active — not practical for routine validation. The 52 fields that passed in the 2026-05-02 run represent what was visible in a cold/hot-start air-start configuration.

### 3. `SAI.reference` (aliased as `SAI_PITCH_TRIM`)

This is the SAI cage / reference-symbol adjustment knob (mouse-wheel rotated in the cockpit). Its `argLim` is `[0.375, 0.625]` — a narrow continuous range, not a 0.0–1.0 axis. The script calls `pushSeqCmd(dt, 'SAI_PITCH_TRIM', int16(0.5), ...)` expecting a 0.5-scaled value. Verify during live validation that the scaling produces the intended centered / uncaged state.

### 4. Ambiguous: `CMDS_PWR_SOURCHE_SW` → `CMDS.RwrSrc`

The BIOS name suggests "power source" but the in-script comment says "CMDS RWR SWITCH". Aliased to `CMDS.RwrSrc` (RWR 555 Switch). Verify intent during live validation.
