# DCS Native Control Extraction — Ka-50 Blackshark II

Module-specific extraction notes for the Ka-50 Blackshark II (BSII).  Read `general.md` first for universal patterns.  The Ka-50 is the **oldest module** in DCS and was the most fragile to extract; the notes below are organised around the things that bit us in order.

> **Note on BSII vs BSIII:** DCS ships *two* installation directories — `Mods/aircraft/Ka-50/` (Blackshark II) and `Mods/aircraft/Ka-50_3/` (Blackshark III).  DCS BIOS exposes them as a single shared module: `Module:new("Ka-50", 0x1800, { "Ka-50", "Ka-50_3" })`.  `LoGetSelfData().Name` returns `"Ka-50"` for BSII and `"Ka-50_3"` for BSIII.  This guide and `extract_Ka50.py` cover BSII.  See `Ka-50_3.md` for BSIII — it uses a separate extractor (`extract_Ka50_3.py`) and has its own startup script, but all Lua pain-points documented here apply equally to BSIII.

## Command Tables

Only **2 command tables** — same legacy pattern as the Mi-8:

| Table | Count | Notes |
|---|---|---|
| `Keys` | 552 | Global key commands, fixed integer IDs |
| `device_commands` | 50 | Generic `Button_1..Button_50` (loop-generated) |

All clickable elements in `clickabledata.lua` reference `device_commands.Button_N`, dispatched per-device by the owning device's command handler.  Same implication as Mi-8: the generator falls back to `<DEVICE>.<ELEMENT_NAME>` naming because there is no per-system command table to mine.

`deviceTableMap` resolved 43 of 64 devices to a command table; the remaining 21 are display-only / passive devices (gauges, indicator surfaces) with no clickable elements logging command access.

## Ka-50-Specific Extraction Pain Points

These were the things that broke when first running `extract_Mi24P.py` against Ka-50 source.  All fixes are baked into `extract_Ka50.py`.

### 1. Lua 5.5 rejects Lua 5.1 escape sequences (NEW pattern)

Ka-50's `clickabledata.lua` line 202 and `Hint_localizer.lua` (10+ lines) wrap multi-position labels in literals like `"Navigation Lights 10\% / 30\% / 100\% / Off"`.  In Lua 5.1 the unrecognised escape `\%` was silently treated as a literal `%`.  In Lua 5.5 (which lupa ships) it is a hard parse error: `invalid escape sequence '\%'`.

**Fix:** Override `dofile` and `loadfile` to read source as bytes and strip the leading backslash from any `\X` where X is not in the valid escape set (`abfnrtv\\"'\n0-9xz`).  See `_sanitizeLua` and the `dofile`/`loadfile` re-definitions in `extract_Ka50.py`.  This is reusable for any other old module that may have the same problem.

### 2. `LockOn_Options` deep-nested key access

`device_init.lua` reads `LockOn_Options.flight.padlock`, `LockOn_Options.time.hours`, `LockOn_Options.cockpit.use_nightvision_googles` (sic — that typo is in DCS source).  It also performs **arithmetic comparisons** on these (`if LockOn_Options.time.hours <= 7 then ...`).

**Fix:** Replace `LockOn_Options` with a fully-equipped magic table whose metatable defines:
- `__index` returning a fresh nested magic table
- `__lt` / `__le` / `__eq` returning `false`
- `__add` / `__sub` / `__mul` / `__div` / `__mod` / `__pow` / `__unm` returning `0`
- `__concat` returning `""`
- `__call` returning `nil`

Without the comparison metamethods, `LockOn_Options.time.hours <= 7` raises `attempt to compare table with number`.

### 3. `Hint_localizer.lua` requires `i_18n.get_locale()`

`Hint_localizer.lua` calls `i_18n_.get_locale()` (returns language, country) before defining `LOCALIZE`.  The Mi-24P `i_18n` mock only stubbed `translate`; Ka-50 needed `get_locale` too.  Also added a top-level `LOCALIZE(s) = s` fallback so that if `Hint_localizer.lua` fails to load for any reason, downstream files still parse.

### 4. JSON encoding for non-ASCII names

Ka-50 element hints contain Cyrillic characters and non-ASCII punctuation (en-dashes, etc.).  The pre-existing `tools/generateControlMapping.py` opened files with the platform default codec and crashed on Windows (cp1252) when reading the Ka-50 extraction JSON.  Fixed inline by adding `encoding='utf-8'` to all three `open()` calls in `generateControlMapping.py` and `ensure_ascii=False` to the output write — a latent bug that just happened never to fire on the prior all-ASCII modules.

### 5. Harmless warnings during extraction

The following sub-page / device files raise errors during extraction but do not affect the final output (they are pages the text-field extractor probes opportunistically):

- `Fonts/symbols_locale.lua`, `Fonts/fonts_cmn.lua` — file does not exist
- `Scripts/fonts.lua` — needs `cp1251_after_128_due_192` global / `add_cyrillic_capitals()`
- `Scripts/KNEEBOARD/declare_kneeboard_device.lua` — file does not exist
- `Scripts/SHKVAL/SHKVAL_page.lua` — needs `SetDefaultClip()` (graphics-only)
- `Scripts/ABRIS/ABRIS_init.lua` — needs `SelfHeight` arithmetic
- `Scripts/EKRAN/Indicator/EKRAN.lua` — `LOCALIZE` used at indicator-page scope
- `Scripts/Devices_specs/ARK.lua` — needs `get_terrain_related_data()`
- `Scripts/ARK/ARK_MAIN_page.lua`, `Scripts/ABRIS/BAKE/init.lua`, `Scripts/SHKVAL/BAKE/init.lua` — graphics-only / `LOCALIZE`
- `Scripts/tools.lua` — file does not exist

If you ever need text-field extraction from these pages, mock the missing globals and provide stubs for the missing files.  For control extraction (the only thing DCSAutoMate needs) they are inert.

## DCS BIOS Migration of `Ka-50 Blackshark II.py`

Same two-stage process as Mi-8MTV2:

1. **`tools/buildBiosNameMap_Ka50.py`** — parses `DCS-BIOS/lib/modules/aircraft_modules/Ka-50.lua` (variable name `Ka_50`), joins each `Ka_50:defineXXX(BIOS_NAME, dev, cmd, arg, ...)` against `config/controlMappings/Ka-50.json` on `(deviceId, commandId, arg)` (with a `(deviceId, commandId)` pair fallback), and emits:
   - `tools/biosNameMap_Ka-50.json` — confident BIOS_NAME → canonical map (281 entries, 98.6 % of the 285 BIOS defines)
   - `tools/biosNameMap_Ka-50.unmapped.json` — 4 BIOS entries with no canonical match
   - `tools/biosNameMap_Ka-50.audit.md` — multi-position discretes for human verification (empty for Ka-50; see "Audit notes" below)

   **Important builder enhancement:** Ka-50's canonical mapping has 11 multi-position discretes whose top-level `deviceId`/`commandId` are `null` and whose per-position `(deviceId, commandId, value)` triples live inside `positionMap[]`.  The Mi-8MT version of the builder only indexed the top-level fields, so these 11 controls would not have been found.  `buildBiosNameMap_Ka50.py` extends `buildIndexes()` to also index every `positionMap[]` entry's `(dev, cmd, arg)` (with a dedupe pass).  This is general and should be backported to other modules' builders.

2. **`tools/applyNameMap.py`** — applies the map with longest-first word-boundary regex replacement (78 unique BIOS names → 191 replacements in the script).

   Followed by standard cleanup per `.agent/research/script-migration-patterns.md`:
   - Removed the `int16()` helper definition.
   - Rewrote `int16(-0.03)` → `-0.03` for the 8 SAI cage-knob calls (the canonical `STBY_ADI.RES_AGD_PTR_arg597` is a `relative` control with `sendProtocol: C`; relative passthrough means the script sends the small float delta directly).

### Audit notes

Ka-50's BIOS file uses the **count-based** `defineMultipositionSwitch(name, dev, cmd, arg, count, step, ...)` signature instead of the **label-array** form (`positions = {"Off","Low","High"}`).  The audit script's `POSITIONS_RE` regex finds nothing to extract, so `biosNameMap_Ka-50.audit.md` ends up empty.  This is fine: across the prior 5 module migrations, every multi-pos discrete index agreed between BIOS and canonical anyway, so the audit has historically produced zero value-changes.  If someone wants to reinstate label-based audits for Ka-50, the labels live inline in the BIOS define's trailing description string (`"Navigation Lights 10% / 30% / 100% / Off Switch"`), not in a `positions` table.

### BIOS-only synthesised controls left unmapped

The 4 unmapped BIOS entries — `DOOR_HDL`, `R800L1_RADIO`, `R828_RADIO`, `SC_ODS_MODE` — are DCS BIOS synthesising controls that don't exist in the native cockpit definitions.  None of them are referenced by `Ka-50 Blackshark II.py` so no fix-ups were needed.  Per the project preference, native always wins: if a future script needs one of these, it must be re-expressed against a control that does exist in `config/controlMappings/Ka-50.json`.

### Module-specific quirks in the script

- **No string-concat relatives, no dynamic name construction, no `scriptCockpitState` reads** — the migration was a pure name swap plus the int16/relative cleanup above.
- **No Shutdown function** (Cold Start + Hot Start only).
- **8 consecutive `int16(-0.03)` calls** for SAI cage-knob: kept the 8 calls intact (each step rotates the knob a small amount) and replaced each with `-0.03`.

### Harmless warnings during extraction

See "Ka-50-Specific Extraction Pain Points → 5" above.

## Two clickabledata patterns Ka-50 forced us to handle

These bit us during validation and required generator + extractor changes.  Both are general patterns (likely appear in other legacy modules) — see `.agent/research/dcs-native-control-types.md` for the cross-module write-up.  This section just records the Ka-50 manifestations.

### Helper-tagged covers (`animated_guard_switch`)

22 Ka-50 covers/guards (ignition cover, fire-extinguisher cover, EKRAN test cover, jettison guard, etc.) are constructed by the `animated_guard_switch` helper inside `clickabledata.lua`.  The returned element looks structurally like a continuous range (no `class_type.TUMB`, just argLim with many steps), so the generator's default heuristic would emit them as 101-position pseudo-discretes.  The validator opens 23 cover/guard controls total; `ADI.TEST-COVER-IKP-PTR` is the extra normal two-action `TUMB` cover.

**Fix:** `tools/extractUtils.py` installs a *helper tagger* that wraps `animated_guard_switch` so every element it builds gets a `helper = 'animated_guard_switch'` field on its extracted JSON record.  `tools/generateControlMapping.py::detectBinaryToggle` keys off that tag and emits a clean 2-position discrete (positions 0 and 1).  See `HELPER_NAMES_TO_TAG` and `installHelperTagger` in `extractUtils.py`.

The tag is preserved through extraction into `config/nativeExtractions/Ka-50.json` (22 elements with `helper='animated_guard_switch'` after the most recent run) so the mapping generator can act on it without re-parsing Lua.

### `.action = {a, b}` override on multi-position rotaries

Five Ka-50 rotaries are built with a standard helper (`multiposition_switch` or `default_3_position_tumb`) and then **override `.action = {cmdA, cmdB}` post-construction** so each direction maps to its own device command:

| Element | Positions | argLim | Step | Inc cmd / Dec cmd |
|---|---|---|---|---|
| `PVI.PVI_SWITCH_PTR` (Master mode) | 7 | [0, 0.6] | 0.1 | Button_27 / Button_26 |
| `WEAP_INTERFACE.PVR_MODE_PTR` (Weapon system mode) | 5 | [0, 0.4] | 0.1 | Button_15 / Button_14 |
| `UV_26.UV26_BOARD_PTR` | 3 | [0, 0.2] | 0.1 | … / Button_14 |
| `NAV_INTERFACE.GYRO_MAG_MAN_HEADING_PTR` | 3 | [0, 0.2] | 0.1 | inc / dec |
| `FIRE_EXTING_INTERFACE.FIREEXT_PTR` | 3 | [0, 0.2] | 0.1 | inc / dec |

**Important DCS semantics (verified by reading Ka-50 `Input/ka-50/keyboard/default.lua` and the device handlers):**

- The DCS clickabledata TUMB handler always sends `clamp(currentArg + argValue, argLim[0], argLim[1])` to the device command — i.e. the *new absolute position*, not a relative delta.
- Every device command on these rotaries is "set state = value", not "step by sign(value)".
- The `.action = {a, b}` override exists **purely for keybinding ergonomics** so the two cockpit-arrow clickspots can have separate keybind targets.  Either command alone can drive the rotary across its full range — the keyboard file confirms this by binding the same single command (e.g. `Button_26`) to absolute `value_down = 0, 0.1, 0.2, …, 0.6` for all 7 positions.

**Initial wrong fix (rejected):** emit as a "wheel" with separate inc/dec command IDs.  Live-tested and broke — sending `+0.1` repeatedly is "set to 0.1" repeatedly, so the knob got stuck at 0.1.

**Final fix:** `tools/generateControlMapping.py::detectDualCommandRotary` detects this pattern *structurally* (2 TUMB sub-controls, same arg, **different** actions, symmetric ±argValue, argLim range > |argValue|), and emits a single-command N-position **discrete** using the inc-side (positive argValue) command.  Detection is purely structural so it covers both the `multiposition_switch` and `default_3_position_tumb` override variants without a helper-tag lookup.

The argLim-spans-multiple-steps test is the discriminator that separates these from legitimate 2-command springloaded switches (which have argLim spanning exactly ±|argValue|, one step) — those keep going through the existing positionMap path.

### Things we deliberately did NOT do

- We did **not** try to call `iCommandPlaneNavChangePanelModeRight/Left` (or any other `iCommand*`) at the mapping/control-panel layer.  Those names are engine-layer abstractions and are NOT reachable via `performClickableAction(deviceId, commandId, value)` — only the device-button command IDs are.
- We did **not** add synthetic +/- "step" buttons to the discrete control card in DCSControlPanel.  Architectural principle: `config/nativeExtractions/<module>.json` and `config/controlMappings/<module>.json` stay 1:1 with what the DCS module's Lua actually exposes.  Synthetic per-control conveniences (relative knob stepping, multi-press macros, etc.) are implemented in DCSAutoMate startup scripts (`DCSAutoMateScripts/*.py`) on an as-needed basis — we already have a powerful Python scripting engine there.
