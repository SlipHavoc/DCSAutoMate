## Critical Quirk: All Command Tables Reset to the Same Start

In `command_defs.lua`, every command table begins by resetting `count` back to `start_command` (3000):

```lua
start_command  = 3000
...
count = start_command
electric_commands = {
    ...
}

count = start_command
fuel_commands = {
    ...
}
```

This means **every command table starts its command IDs at 3001**, independently. Command ID 3001 appears in all 19 tables. Device ID is the sole disambiguator — a given `{deviceId, commandId}` pair uniquely identifies a control because each device binds to exactly one command table.

## No Separate clickable_defs.lua

Unlike most modules, the F-86F defines all ~20 Lua helper functions inline at the **top of `clickabledata.lua`** (lines 23–490). There is no separate `clickable_defs.lua` file. The `installHelperTagger` approach still tags elements correctly because the functions are defined in the same Lua runtime before the elements table is populated.

## Unused Helper Functions

These functions are defined in `clickabledata.lua` but have zero usages in the elements table and thus do not appear in the extraction:

- `default_1_position_tumb`
- `default_button_axis` (BTN+LEV with two different commands and two different args)
- `default_springloaded_tumb`
- `radio_wheel`

## gyromagcompass_commands — Non-Standard Syntax

`gyromagcompass_commands` uses direct arithmetic instead of `counter()`:

```lua
count = start_command
gyromagcompass_commands = {
    F86_gyromagcompass_001 = start_command + 1,
    F86_gyromagcompass_002 = start_command + 2,
    ...
}
```

Lua executes this at parse time, so the resulting values are identical to `counter()` output. The extractor handles this correctly without any special casing.

## device_commands — Multi-System Shared Table

`device_commands` is used by at least 5 different device IDs (5, 12, 10, 21, 22, 7). These devices use the generic `device_commands` table rather than a dedicated named table. The deviceTableMap correctly records `device_commands` for each.

## class_type.TUMB_4SIDE

The `Lateral_Alternate_Trim_Switch` element uses `class_type.TUMB_4SIDE`. This requires adding `TUMB_4SIDE = 6` to the `class_type` mock in `createLuaRuntime()`, which is done in `extract_F86F.py`.

## MIRRORS Element — Zero Device

`elements["MIRRORS"]` has `device = 0` and `command = 3001` — a zero-device dummy element used for animation only. The extractor captures it as-is; the mapper's structural fallback will skip it (no valid device-table mapping for device 0).

## Inline Elements (No Helper Tag)

23 elements have no helper function tag (they are defined as inline Lua table literals). These include:
- `Cockpit_Switch_ON-OFF` (canopy)
- `Lateral_Alternate_Trim_Switch` (TUMB_4SIDE type)
- `Emergency_Ingition_Switch`
- `Wing_Flap_Lever`
- Several clock, trim, gun, and sight controls

These go through `processElements()` structural inference in the mapping phase.

## mainpanel_init.lua — get_plugin_option_value

`mainpanel_init.lua` calls `get_plugin_option_value("F-86F","landSeatAdjustF86")` at line 528. This requires mocking `get_plugin_option_value(plugin, key) return nil end`. Without the mock, extraction stops at line 528, but since `dofile(lamps.lua)` runs at line 525 (before the failure), all 76 gauges/lamps are captured regardless.

The mock is included in `extract_F86F.py` to produce clean output.
