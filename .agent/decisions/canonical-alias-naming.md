# Decision: Canonical Control Names + Per-Module Alias Files

**Date:** 2026-04-20
**Status:** **Superseded** — alias layer fully removed.  `config/controlAliases/` directory deleted.  See *2026-04-23 update* at end of this file.
**Scope:** Control name generation, alias resolution, all four supported modules
**Supersedes (partially):** `.agent/decisions/control-naming-dotted-vs-camelcase.md` — the camelCase transform is now replaced by verbatim DCS-Lua keys.

---

## Context

As of Phase 6 of the DCS-BIOS elimination effort, control mapping files were being
generated by a pipeline that took the raw symbols from the module's
`command_defs.lua` + `clickabledata.lua` + `devices.lua` and ran them through:

1. `cmdNameToCamelCase` — lowerCamelCase conversion with hand-rolled rules for
   UPPER_SNAKE, PascalCase, and mixed forms.
2. `hintToCamelCase` — fallback when no command name was resolvable.
3. Suffix stripping (`_EXT`, `_AXIS`, `_ITER`) to collapse sibling variants.
4. Deduplication (`deduplicateName`) appending a device prefix or numeric tag when
   two synthesized names collided.
5. A `CONTROL_NAME_OVERRIDES` dict (per module) for hand-patched exceptions.

This pipeline had three chronic problems:

- **Brittle.** Every new module surfaced bugs in the case-conversion rules
  (e.g. the Mi-24P `ACGeneratorLeft` → `aCGeneratorLeft` leading-abbreviation bug
  documented in `tools/extraction-guides/Mi-24P.md`).
- **Lossy.** Suffix stripping and dedup meant the generated name was *not* a
  reliable key back to the Lua source — you couldn't grep `command_defs.lua` for
  `apuControlSw` and expect to find anything.
- **Inconsistent across modules.** Each module had a slightly different set of
  overrides and special cases, pushing us toward per-module generator scripts
  (`generate_FA18C.py`, `generate_AV8BNA.py`, `generate_AH64D.py`,
  `generate_Mi24P.py`), which fragmented the pipeline.

The existing `.agent/decisions/control-naming-dotted-vs-camelcase.md` had already
concluded that dotted device-prefixed names (`APU.ControlSw`) were clearer than
camelCase. That decision was re-opened in light of the pipeline pain: if we're
going to prefix with the device anyway, why transform the name at all?

## Decision

Use **canonical names derived verbatim from the DCS Lua sources** as the primary
key, and store human-readable short names in a separate **per-module alias file**
that is resolved transparently at runtime.

### 1. Canonical naming scheme

| Source                                     | Canonical form                          |
|--------------------------------------------|-----------------------------------------|
| cmd-backed element                         | `<deviceName>.<cmdName>`                |
| positionMap element (multi-cmd)            | `<deviceName>.<firstCmdName>`           |
| cmd-missing element (cmd not in `command_defs`) | `<deviceName>.cmd_<cmdId>`         |
| gauge / lamp                               | `arg.<N>`                               |
| indicator field                            | `ind.<indicationId>.<fieldName>`        |

Separator is `.`.  Names are the **exact strings** from the Lua — no case
conversion, no suffix stripping, no deduplication.  Collisions (same `deviceName`
+ `cmdName` appearing on multiple elements) are resolved last-write-wins with a
warning; in practice they only surface for things like the Mi-24P CPT_MECH wiper
switches that genuinely share a command name.

### 2. Alias file schema

`config/controlAliases/<moduleName>.json`:

```json
{
  "module": "FA-18C_hornet",
  "aliases": {
    "<canonical>": {
      "name": "<short human-friendly name>",
      "description": "<optional>",
      "aliases": ["<optional extra aliases>"]
    }
  },
  "_unmatched": ["<old-mapping controls that didn't match any canonical>"]
}
```

Defaults are omitted.  `_unmatched` is a review aid produced by the migrator and
is ignored at runtime.

### 3. Runtime lookup order (`DCSDirectManager._buildControlIndex`)

1. Exact match against canonical key.
2. Exact match against `aliases[canonical].name`.
3. Exact match against any entry in `aliases[canonical].aliases[]`.

Scripts continue to address controls by short names (`apuControlSw`,
`gearHandle`, etc.) transparently.

### 4. Migration tooling

- `tools/migrateToCanonical.py --module X --old OLD.json --canonical NEW.json --out ALIAS.json`
  cross-references an old camelCase mapping against a freshly regenerated canonical
  mapping using `(deviceId, commandId)` → `positionMap[0]` → `(indicationId, fieldName)` →
  unique `arg` matching, and produces the alias file.  Unmatched old controls go into
  `_unmatched` for review.

- `tools/generateControlMapping.py` now emits canonical names directly.  All four
  per-module generators (`generate_FA18C.py`, `generate_AV8BNA.py`, `generate_AH64D.py`,
  `generate_Mi24P.py`) have been deleted.  The shared generator achieves parity with
  the last-remaining Mi-24P dedicated generator via two changes:
  (a) **Deterministic device→table mapping** via `tools/extractUtils.py` lupa
      metatables — resolves most `cmd_<id>` fallbacks to real command names (e.g.
      `CLOCK_O.cmd_3002` → `CLOCK_O.Button_2`).
  (b) **Uniform-arithmetic collapse for positionMaps** — elements with multiple
      sub-controls on the same `arg` sharing a single `action` (even with opposing
      argValues and symmetric argLim) are emitted as plain `discrete` controls with
      computed `step`/`positions` instead of `positionMap` entries, because the
      command itself accepts absolute argValues.  Mirrors what `generate_Mi24P.py`
      always did and matches the live-validated Mi-24P baseline.
  (c) **TUMB+relative classified as `discrete`**, not `relative` — matches
      dedicated generator and live-validated Mi-24P Jadro radio dial behavior.

## Consequences

### Positive

- **Names round-trip to the Lua source.**  Grepping `command_defs.lua` for
  `ControlSw` finds every `APU.ControlSw` control.  Debugging is meaningfully easier.
- **Pipeline is dramatically simpler.**  Roughly 400 lines of name-synthesis code
  (case conversion, suffix stripping, dedup, collision handling) were deleted.
- **No per-module pipeline forks.**  One generator handles FA-18C, AV-8B, AH-64D,
  and Mi-24P identically.
- **Aliases are editable separately** from the generated mapping.  A user-friendly
  name can be added or fixed without regenerating anything.
- **Validated live on all four aircraft with zero regressions** (Mi-24P 1002/30/162,
  FA-18C 470/17/4, AV-8B 257/8/12, AH-64D 614/16/0).

### Negative / accepted trade-offs

- **Canonical names are longer and less ergonomic** than the old camelCase
  (`APU.ControlSw` vs `apuControlSw`).  Users should normally write scripts against
  the aliases, not canonicals.  This is mitigated by the runtime resolver —
  existing scripts kept working unchanged.
- **Two-file system** (mapping + aliases) adds one more artifact per module.  This
  is the price of decoupling the stable generated data from the curated human-facing
  data.

All regressions between old and new mappings were analyzed and explained:

single canonical; these were informational and did not represent lost functionality.

## 2026-04-23 update — aliases slated for retirement

**New status:** the canonical-name half of this decision stands; the alias-file half is being rolled back.

### What changed

During F-16C conversion on branch `eliminate-dcs-bios`, it became clear that the alias layer is actively harmful to script sharability:

- Scripts that reference aliases only work in the author's config.  If a user shares a script, the recipient also needs a matching alias file — but we have no mechanism to ship or version aliases alongside individual scripts, and a user may have multiple scripts per module.
- Canonical names (`Device.Command`, `arg.<N>`, `ind.<id>.<field>`) are stable across every install of the same DCS version, so they are the only names that are actually portable.
- Generating "nice" names from DCS descriptions was abandoned earlier because the descriptions are too inconsistent.  That problem has not changed; the F-16C's SCREAMING_SNAKE aliases are a carryover from DCS BIOS, not a real solution.
- The `description` field already provides human-readable text for logs and UIs, so identifier aesthetics are a non-goal.

### New policy

1. Canonical names are the public script API.  New scripts should use them directly.
2. Script authors who want a shorter local label can assign the canonical name to a module-level constant in their own `.py` file.  No shared aliasing.
3. ~~`config/controlAliases/<module>.json` files are retained during a transition period.~~ **Done — `config/controlAliases/` has been deleted.**
4. ~~In a follow-up branch, all bundled scripts will be rewritten to canonical names.~~ **Done.**
